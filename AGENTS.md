# AGENTS.md: Kingdom Tycoon

Instructions for AI coding agents working in this repo. Read this file and `GAME_DESIGN.md` before doing anything.

## 1. Source of truth
- `GAME_DESIGN.md` is the project spec: pillars, layer roadmap, systems, monetization rules, open decisions.
- If a request conflicts with the spec, **stop and ask**. Do not silently deviate.
- If the spec is silent or ambiguous, ask before guessing. Batch questions (max ~5) and state your default assumption for each so I can just reply "ok".
- Do not resolve items under "Open decisions" yourself. Ask me.

## 2. About the developer
- CS master's student; strong programmer, new to Luau and Roblox.
- Explain Roblox-specific concepts briefly (replication, RemoteEvents, streaming, physics ownership). Skip general programming explanations.
- macOS, VS Code, Rojo (via Aftman), Git/GitHub.
- This project is also a portfolio piece: prefer clean architecture, clear commits, and documented decisions over clever shortcuts.

## 3. Workflow rules
1. Work on **one milestone at a time** (see roadmap in `GAME_DESIGN.md`). Do not implement future milestones or "helpful extras".
2. **Plan first.** Before editing, list the files you will create or change and your assumptions. Wait for my go-ahead on any non-trivial change.
3. Keep changes small and reviewable. Do not rewrite unrelated files.
4. Do not run `git commit` or `git push` unless I ask. Suggest a commit message (Conventional Commits: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`).
5. Never delete or overwrite my files without asking.
6. End every task with: what changed, how to verify it (what I should see in Studio's Output), and anything I should double-check.

## 4. Luau rules
- Luau only. Use `task.wait()`, `task.spawn()`, `task.delay()`. Never `wait()`, `spawn()`, `delay()`.
- `--!strict` at the top of files where practical; type-annotate public functions.
- Use only current, non-deprecated Roblox APIs. If unsure an API is current, say so and I'll check the docs.
- Modular design: ModuleScripts hold logic; entry scripts are thin bootstrappers.
- No global state via `_G` or `shared`.
- Clean up connections and instances (Maid/Janitor pattern or explicit `:Disconnect()` / `:Destroy()`).
- Constants live in shared config, not scattered as magic numbers (e.g. `MAX_ARMY_SIZE = 10`).

## 5. Security and architecture rules
- **Server-authoritative.** The client only requests; the server validates and decides. Never trust client-sent values (prices, damage, positions, currency).
- Every RemoteEvent/RemoteFunction handler must validate argument types, ranges, and player state, and rate-limit where relevant.
- Purchases, rebirths, PvP toggling (2-minute cooldown), and combat are validated on the server.
- Player data goes through the data service only (ProfileStore, once added). Include a schema version field and migration handling.
- Monetization rules from the spec are hard constraints: no pay-to-win, no damage-boost purchases.

## 6. Rojo rules
- Rojo syncs **files into Studio, one way**. Edit scripts in VS Code only, never in Studio's script editor.
- File naming: `Name.server.luau` (Script), `Name.client.luau` (LocalScript), `Name.luau` (ModuleScript), `init.*.luau` for folder-as-script.
- Any change to `default.project.json` must come with an explanation of what it maps and whether it could overwrite or delete anything in my existing Studio place.
- Do not commit `.rbxl`/`.rbxlx` place files, `sourcemap.json`, or installed packages.

## 7. Visual and map assets
- Maps, models, and terrain are built in Studio, not generated by scripts. Code should **clone templates** (e.g. from `ServerStorage`) and attach behavior, rather than constructing complex models from `Instance.new` calls.
- Simple UI may be built in code. Complex visuals: tell me what asset I need to build, its required names/attributes/tags, and how your code expects to find it (a short "asset contract"), then wait for me.
- Document every asset contract in section 10 below.

## 8. Performance rules
- Cap NPCs and armies (army cap is 10 soldiers per player). Prefer simple server AI and client-side visuals.
- Avoid per-frame server loops where an event or timed tick works.
- Note any performance trade-off in the PR/commit description; we document optimizations for the portfolio.

- The `init.*` files make Server/Client script instances with Services/Controllers
  as children. StarterPlayerScripts clones Client and its descendants into each
  player's PlayerScripts. ReplicatedStorage is visible to clients; do not put
  secrets or authoritative data there.
- Server startup order: require DataService, PlotService, FarmService, then ExampleService → call all
  services' Init() → call all services' Start() → log ServerBootstrap Ready.
  DataService loads player profiles asynchronously; Ready is not a data-ready signal.
  The optional Studio-only test switch runs DataLayerTests afterward via task.spawn.
- Client startup order: require ExampleController, PlotController, CameraController → call all controllers' Init()
  → call all controllers' Start() → log ClientBootstrap Ready.
- Lists are explicit and ordered. Modules implement typed `Init(): ()` and
  `Start(): ()` functions called with dot syntax. Require/Init must avoid gameplay
  side effects; Start must return promptly. Errors halt that bootstrap before Ready.
  The server and client bootstraps have no shared ordering guarantee.
- Wally output stays at the repository root and is generated/ignored. ProfileStore
  1.0.3 is pinned as a server dependency. Track wally.lock; never edit generated packages.
- DataService is the sole gameplay access path: GetSnapshot returns detached data;
  Update validates a non-yielding draft, rejects errors/stale revisions, and copies
  committed data. No profiles or player data are replicated in this milestone.
- Schema v1: Gold = 0, Rebirths = 0, PurchasedBuildings = {}, SchemaVersion = 1.
  Future migrations run sequentially on copies when individual records load;
  no historical steps exist yet. Invalid/unsupported/newer records are rejected.
- Studio defaults to Mock; optional Persistent uses only the test store. Published
  servers use only the live store. Persistent loads refuse unavailable API access
  and preflight raw envelopes (one extra read/join, not atomic with session locking).
  ProfileStore supplies its default 300-second autosave and session locking;
  DataService releases on leave/shutdown, rejects inactive updates, and disconnects
  handlers after final saves. See README for API contracts and verification details.
- Workspace and Lighting are Studio-owned and unmapped; the template Baseplate
  and FilteringEnabled entry were removed. A fresh Rojo build contains code only.
- Unknown instances at the DataModel/service boundaries are preserved explicitly.
  Server, Client, Shared, Packages, and ServerPackages containers are source-owned;
  matching instances can be overwritten/replaced and unknown descendants deleted.
  SoundService retains RespectFilteringEnabled = true and can overwrite that
  property's Studio value. Save a copy and review the Rojo sync diff, especially
  when changing an existing sync session's mappings.
